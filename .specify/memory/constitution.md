# WordPress Premium Development Constitution

This constitution governs the development of **every WordPress/WooCommerce website** built under
this workflow — not just a single project. It was first ratified while building **Aurelia Home**,
a premium WooCommerce furniture & décor store, and is written to generalize to all future
WordPress-based engagements (portfolio, client, or production work). Individual projects add a
`specs/<feature>/` layer of concrete requirements on top of these non-negotiable baseline rules.

## Core Principles

### I. WordPress-Native, WooCommerce-Native Architecture (NON-NEGOTIABLE)

Every site MUST be built on WordPress-native and WooCommerce-native extension points. Core MUST
NOT be modified:

- MUST NOT modify WordPress core files.
- MUST NOT modify WooCommerce core files.
- MUST NOT modify the source of any third-party plugin.
- Custom behavior MUST be implemented exclusively through a custom theme, a custom plugin,
  WordPress/WooCommerce hooks (actions/filters), the WordPress REST API, WordPress APIs
  (Settings, Options, Transients, Cron), and custom blocks/patterns where appropriate.
- Presentation (templates, styling, UI components) belongs in the theme. Business logic,
  data integrity, and integrations belong in a custom plugin. Business-critical functionality
  MUST NOT live exclusively in the theme, since themes are more likely to be swapped or restyled.
- Custom database tables are DISALLOWED by default. WordPress posts, custom post types,
  taxonomies, WooCommerce data structures, and the options API MUST be used first. A custom
  table MAY be introduced only when justified by a documented architecture or performance need.

**Rationale**: Modifying core or plugin source creates unmergeable forks that break on every
update, destroy security patching, and are the single most common cause of catastrophic WordPress
site failure. Native extension points keep the site upgradable indefinitely.

### II. Security-First Development (NON-NEGOTIABLE)

Security is not a phase — it is a property every change MUST hold before merge. Every input path
and output path MUST satisfy:

- Sanitize all input, validate all input, escape all output (`esc_html`, `esc_attr`, `esc_url`,
  `wp_kses`, etc.) — no exceptions for "trusted" admin-only fields.
- Use nonces for every form and state-changing request; verify capability (`current_user_can`)
  before every privileged action.
- REST API endpoints MUST authenticate/authorize appropriately and MUST treat all payloads as
  untrusted, including payloads generated by AI systems.
- Prevent SQL injection (always use `$wpdb->prepare()` or WP data APIs), XSS, and CSRF as a
  default posture, not an afterthought caught in review.
- No secrets, API keys, passwords, or credentials MAY be hardcoded or committed to Git. Secrets
  MUST be read from environment/configuration mechanisms (`.env`, `wp-config.php` constants
  outside version control, host-level secret stores).
- No sensitive information (keys, tokens, internal identifiers) MAY be exposed in frontend
  JavaScript or HTML source.
- Raw payment card data MUST NEVER be stored; payment processing MUST go through a PCI-compliant
  gateway.
- Any AI-assisted feature MUST NOT be permitted to modify prices, inventory, orders, customer
  data, or user accounts, create privileged users, or execute arbitrary SQL/PHP. AI output is
  always untrusted input and MUST pass through the same validation as user input.

**Rationale**: WordPress's ubiquity makes every site a scanning target from the moment it is
public. A single unescaped output or missing capability check is sufficient for full compromise.
Security debt compounds silently until it is exploited, so it MUST be enforced at write-time.

### III. World-Class UI/UX & Design Excellence

Every site MUST look and behave like a premium international e-commerce/brand experience, not a
default WordPress theme:

- Editorial layouts, strong typographic hierarchy, generous whitespace, high-quality imagery, and
  clear visual hierarchy are required baseline quality bars.
- Micro-interactions MUST be purposeful and subtle — never decorative noise.
- Avoid generic WordPress/template appearance, outdated gradients, excessive rounded cards,
  excessive animation, and visual clutter (including excessive popups).
- Usability MUST be prioritized over visual effects: every interactive element MUST have an
  obvious affordance, state (hover/active/disabled/loading), and outcome.
- Every custom, AJAX-driven feature (search, filters, add-to-cart, wishlist, AI assistant) MUST
  define an explicit loading state and an explicit failure/empty state — never a silent hang or a
  blank screen.

**Rationale**: The differentiator between a "WordPress site" and a "premium product" is almost
entirely in these details. This is the primary criterion by which client and portfolio work is
judged, and it is cheap to get right early and expensive to retrofit.

### IV. Performance & Scalability

Sites MUST be engineered to load fast and stay fast as catalog and traffic scale:

- Target excellent Core Web Vitals (LCP, INP, CLS) on every template type (home, archive,
  product, cart, checkout).
- Images MUST be served at correct dimensions, compressed, and lazy-loaded where off-screen.
- JavaScript and CSS MUST be minimal and scoped — scripts/styles MUST NOT load on pages that do
  not use them.
- Render-blocking resources MUST be minimized; defer/async non-critical scripts.
- Every plugin added MUST be justified against its performance cost; do not install a plugin for
  functionality that can reasonably be hand-rolled at lower overhead.
- Database queries introduced by custom code MUST avoid N+1 patterns and MUST use WordPress
  object caching / transients for expensive, repeatable lookups.
- Architecture MUST anticipate catalog growth (hundreds to thousands of products) and traffic
  spikes without requiring a rebuild — caching layers and CDN-compatible asset delivery MUST be
  assumed from the start, not bolted on later.

**Rationale**: E-commerce conversion is directly, measurably sensitive to load time. Performance
regressions found post-launch are far costlier than performance budgets enforced during
development.

### V. Mobile-First, Fully Responsive Design

The majority of e-commerce traffic is mobile. Every feature MUST be designed mobile-first, then
enhanced for larger viewports:

- MUST support, at minimum, viewport widths: 320, 375, 390, 414, 768, 1024, 1280, 1440, 1920px.
- Mobile layouts MUST NOT be a compressed/shrunk desktop layout — navigation, filtering, product
  cards, cart, and checkout MUST be intentionally designed for touch and small viewports.
- Tap targets, gestures (swipe for galleries), and mobile-specific patterns (bottom sheets, sticky
  add-to-cart) MUST be considered wherever they improve usability.

**Rationale**: A responsive breakpoint that merely reflows desktop content is a common source of
abandoned mobile carts. Mobile-first design forces the simpler, higher-converting experience by
default and scales up cleanly.

### VI. Accessibility (WCAG 2.2 AA)

Every site MUST conform to WCAG 2.2 Level AA as a floor, not a stretch goal:

- Full keyboard navigability and visible focus states on every interactive element.
- Semantic HTML and correct heading hierarchy; forms have proper labels and error messaging.
- All meaningful images have alt text; decorative images are marked as such.
- Sufficient color contrast; information MUST NOT be conveyed by color alone.
- Modals, dropdowns, product variation pickers, and other custom widgets MUST be
  screen-reader-accessible (correct ARIA roles/state), not just visually functional.

**Rationale**: Accessibility is both a legal exposure area for commercial sites and a direct
expansion of addressable customers. Retrofitting accessibility after launch is materially more
expensive than building it in from the first component.

### VII. SEO-Ready by Architecture

Every site MUST be structured so organic discoverability is a byproduct of the architecture, not
a separate project phase:

- Semantic HTML, correct heading hierarchy, SEO-friendly URLs, canonical URLs, XML sitemap
  compatibility, and breadcrumbs are required.
- Structured data (schema.org) MUST be present for Product, Organization, and Article types where
  applicable; Open Graph and Twitter/X metadata MUST be present on shareable pages.
- Custom SEO handling MUST NOT conflict with, and MUST remain compatible with, major SEO plugins
  (e.g., Yoast, Rank Math) so the site owner retains the option to use one.

**Rationale**: Organic search is typically the highest-ROI acquisition channel for e-commerce.
SEO problems baked into markup/architecture are far harder to fix than content-level SEO issues.

### VIII. Specification-Driven Development & Testing Discipline

No implementation work begins before the relevant specification is read and understood:

- Before writing code for a feature, the applicable spec MUST be read in full, ambiguities MUST
  be identified and raised to the user, and dependencies/risks MUST be identified before
  implementation starts.
- If a requirement conflicts with another requirement or with this constitution, STOP and report
  the conflict — do not silently choose one interpretation.
- Features MUST NOT invent functionality not specified without explicit user sign-off.
- Every feature MUST be validated against: functional testing (the feature's own flows),
  responsive testing (the breakpoints in Principle V), cross-browser testing (Chrome, Edge,
  Firefox, Safari where available), and — where the feature touches trust boundaries — security
  testing (unauthorized requests, CSRF, XSS, SQLi vectors, permission escalation).
- User-facing errors MUST be useful and MUST NOT leak PHP errors, stack traces, or internal
  implementation details.
- Manual QA alone is NOT sufficient for commerce-critical logic. Custom business logic in the
  plugin (pricing rules, coupon logic, AI query parsing, custom REST endpoints, order/stock
  mutations) MUST have automated unit/integration tests (PHPUnit + the WordPress/WooCommerce test
  scaffolding). The core purchase path (add to cart → apply coupon → checkout → order
  confirmation) MUST have an automated end-to-end test (e.g., Playwright/Cypress) that runs before
  a release is considered ready, so a regression in the revenue path is caught before a customer
  finds it.

**Rationale**: This project's entire methodology is Spec-Driven Development; skipping
specification review reintroduces the "silent scope substitution" failure mode SDD exists to
prevent, and untested responsive/security paths are the most common source of late-stage rework.
Manual QA catches what a human remembers to click; automated tests catch what a human forgets to
re-check after an unrelated change — and the checkout path is the one flow where that gap is most
expensive.

### IX. Clean, Modular, Maintainable Code

Code is written for the next maintainer, not just to pass today's review:

- Follow WordPress Coding Standards for PHP, JS, CSS/Sass, and HTML.
- Code MUST be modular and reusable — avoid huge functions, duplicated logic, and global-variable
  coupling.
- No hardcoded URLs, credentials, or environment-specific values; use configuration/constants.
- Every non-obvious piece of logic (a workaround, a subtle invariant, a security-relevant
  decision) MUST carry a short comment explaining *why*; code that is self-evident from naming
  needs no comment.
- Plugin dependencies MUST be kept to the minimum necessary and every dependency MUST be
  documented (why it was chosen, what it replaces if removed).

**Rationale**: Portfolio and client WordPress sites are long-lived and frequently handed off to
other developers or the client's own team. Unmaintainable code is a direct liability to the
client relationship and to the developer's reputation.

### X. AI Feature Safety (when a project includes AI functionality)

Where a project adds an AI-assisted feature (e.g., natural-language product discovery), the
following are NON-NEGOTIABLE in addition to Principle II:

- The request path MUST be: client → AI UI → custom validated REST endpoint → input validation →
  constrained data lookup (e.g., WooCommerce product search) → AI processing → structured
  response. The AI layer MUST NOT have direct write access to orders, prices, inventory, or
  accounts.
- AI output MUST be treated as untrusted and MUST be validated/sanitized before display or use;
  arbitrary AI-generated code MUST NEVER be executed.
- AI features MUST degrade gracefully (explicit "AI unavailable" state) rather than blocking core
  commerce flows if the AI backend is unreachable.

**Rationale**: AI assistants are a novel, less-audited attack surface on top of an already
security-sensitive commerce stack; treating their output as equivalent to anonymous user input
closes the most likely exploitation path.

### XI. Privacy, Data Protection & Compliance (NON-NEGOTIABLE)

Every site handles personal data (customer accounts, orders, addresses, newsletter emails) and
MUST treat that data as regulated, not incidental:

- Consent MUST be explicit and unbundled: newsletter/marketing signup MUST have its own opt-in
  and MUST NOT be pre-checked or implied by checkout completion; consent/privacy messaging MUST
  be shown at every collection point.
- A Privacy Policy and Terms & Conditions page MUST exist and MUST accurately describe what data
  is collected, why, how long it is retained, and which third parties (payment gateway, analytics,
  email provider) receive it.
- Analytics and tracking (Google Analytics, GTM, Meta Pixel, etc.) MUST be loaded only through
  configuration/settings — tracking IDs MUST NOT be hardcoded — and MUST respect applicable
  consent requirements (e.g., no tracking scripts firing before consent where consent-gating
  applies).
- Data collection MUST be minimized to what the feature actually needs; MUST NOT collect a field
  "in case it's useful later."
- Customers MUST have a practical path to request access to, export of, or deletion of their
  personal data (WordPress's built-in personal data export/erasure tools MUST be kept functional,
  not disabled by custom code).
- Data retention MUST be intentional: define how long guest checkout data, abandoned cart data,
  and marketing consent records are kept, and document it.

**Rationale**: Data-protection failures (silent tracking, bundled consent, no erasure path) are
both a legal liability for the client and a trust failure for end customers; regulators and
platforms (payment processors, ad networks) increasingly enforce this even on small stores.

## Technology Stack Standards

- **Core platform**: WordPress (latest stable), WooCommerce (latest stable), PHP 8.1+,
  MySQL/MariaDB.
- **Frontend languages**: HTML5, modern CSS (Sass/PostCSS acceptable), JavaScript (ES6+,
  framework-free by default).
- **Architecture**: Gutenberg / WordPress block architecture and `theme.json` for design tokens;
  custom WooCommerce template overrides only where the default template cannot meet the design;
  WordPress REST API for any custom data exchange; WP-CLI for development and demo-data tooling.
- React/Next.js or any headless frontend MUST NOT be introduced as the primary rendering layer
  unless a project's specification explicitly requires a headless architecture — the default
  deliverable is a WordPress-native theme, because that is the competency being demonstrated and
  the ownership model clients expect.
- Theme structure MUST separate concerns: `assets/` (css/js/images), `inc/` (PHP includes),
  `parts/`, `patterns/`, `templates/` for the theme; business logic, custom REST endpoints, and
  integrations live in a co-located custom plugin (e.g. `wp-content/plugins/<project>-core/`).
- Environments MUST be separated (development / staging / production) with environment-specific
  configuration; no environment-specific secret ever committed to Git.

## Security Requirements

This section operationalizes Principle II as a checklist every feature MUST satisfy before it is
considered done:

- [ ] All user input sanitized and validated server-side (never trust client-side validation
      alone).
- [ ] All dynamic output escaped appropriately for its context.
- [ ] Nonces present and verified on every form/state-changing AJAX/REST call.
- [ ] Capability checks (`current_user_can`) present on every privileged action.
- [ ] REST endpoints reviewed for auth, rate-limiting exposure, and input-shape validation.
- [ ] No secrets, keys, or credentials in source control, comments, or frontend JS.
- [ ] Dependency/plugin list reviewed — no unmaintained or unnecessary plugin introduced.
- [ ] File uploads (if any) restricted by type/size and stored outside directly-executable paths
      where feasible.
- [ ] Security-relevant changes exercised against: CSRF, XSS, SQL injection, permission
      escalation, and (if applicable) AI prompt-manipulation vectors.

## Production Readiness & Operations

Launch is not the finish line — every site MUST be operable after it goes live:

- **Backup & disaster recovery**: automated backups (database + files) MUST be configured before
  a site goes to production, on a schedule appropriate to change frequency (daily minimum for an
  active store). Backups MUST be stored off-server. A restore procedure MUST be documented and,
  for production launches, actually tested at least once — an untested backup is not a backup.
- **Observability & monitoring**: production sites MUST have error logging that survives beyond
  the PHP debug log used in development (e.g., a logging plugin/service or host-level log
  aggregation), and MUST have uptime/availability monitoring for the storefront and checkout flow.
  Critical failures (payment gateway errors, checkout failures, AI backend outages) MUST be
  logged in a way a developer can review after the fact — not just surfaced as a one-time user
  error state.
- **Internationalization readiness**: all user-facing strings in custom theme/plugin code SHOULD
  be wrapped for translation (`__()`, `_e()`, text domains) even when a project ships English-only,
  so a future localization does not require touching business logic. Layouts SHOULD tolerate
  ~30% text expansion (for future non-English locales) rather than relying on fixed-width text
  containers. Full RTL support is only REQUIRED when a project's specification calls for an
  RTL-language locale.
- **Staging/production parity**: the staging environment MUST match production's PHP version,
  WordPress version, WooCommerce version, and active plugin versions before any release is
  validated there. A change MUST be verified on staging before it reaches production; staging
  drifting out of sync with production invalidates that verification and MUST be corrected before
  the next release, not deferred.
- **Transactional email deliverability**: order confirmation, shipping/tracking, password-reset,
  and account emails MUST be sent through a dedicated transactional email service or authenticated
  SMTP (not the hosting provider's default unauthenticated `wp_mail()` pathway), with SPF, DKIM,
  and DMARC configured for the sending domain. Deliverability (inbox vs. spam placement) MUST be
  verified for at least the order-confirmation email before a site is considered launch-ready.

**Rationale**: A store that is fast and secure at launch but has no backup, no error visibility,
no localization headroom, drifting staging, or unreliable order emails degrades into an
unmaintainable liability the first time something breaks in production, a client asks to expand
markets, or a customer never receives their order confirmation — all foreseeable, common failure
modes that are cheap to prevent now and expensive (or reputation-damaging) to fix after launch.

## Development Workflow & Quality Gates

- **Version control**: Git is mandatory. Recommended branch model: `main` (production-ready),
  `develop` (integration), `feature/*`, `fix/*`. Commit messages MUST be meaningful and
  conventional (`feat:`, `fix:`, `perf:`, `security:`, `docs:`, `chore:`).
- **Definition of Done** for any feature, at minimum:
  - [ ] Implemented via native WordPress/WooCommerce extension points (Principle I).
  - [ ] Security checklist above satisfied.
  - [ ] Responsive behavior verified at the breakpoints in Principle V.
  - [ ] Accessibility spot-checked (keyboard nav, focus states, labels, contrast).
  - [ ] No console errors, no PHP notices/warnings/errors in the debug log.
  - [ ] Loading and empty/error states implemented for any async interaction.
  - [ ] Documentation updated (README/SETUP/relevant `specs/*.md`) if setup or usage changed.
  - [ ] Reviewed for scope creep — no unspecified functionality silently added.
- **Documentation**: every project MUST maintain, at minimum, `README.md` and setup/deployment
  instructions sufficient for another developer to stand up the environment from scratch,
  including any demo-data seeding mechanism (WP-CLI script or controlled importer).
- **Knowledge capture**: every user prompt that drives implementation, planning, or debugging
  work MUST result in a Prompt History Record under `history/prompts/`, and every architecturally
  significant decision MUST be offered to the user as an ADR candidate, per the project-level
  agent rules in `CLAUDE.md`. This constitution defines *what* "architecturally significant"
  means in practice: changes to the technology stack, the theme/plugin boundary, the security
  model, or any principle in this document.

## Governance

This constitution supersedes ad-hoc practice for all WordPress projects developed under this
workflow. Where a project-specific `specs/<feature>/plan.md` appears to conflict with a principle
here, the conflict MUST be surfaced to the user before implementation — this document is not
silently overridden by a lower-level artifact.

**Amendment procedure**:
1. Propose the change (what principle/section, what text, why) — typically via `/sp.adr` when the
   change is itself an architectural decision.
2. Determine the semantic version bump:
   - **MAJOR**: a principle is removed or redefined in a backward-incompatible way (e.g.,
     relaxing a NON-NEGOTIABLE rule).
   - **MINOR**: a new principle or materially expanded section is added.
   - **PATCH**: wording, clarification, or typo fixes with no semantic change.
3. Update this file, including the Sync Impact Report comment at the top.
4. Propagate the change to dependent templates (`.specify/templates/*.md`) and `CLAUDE.md` if
   they reference the changed principle by name.
5. Record the amendment date below.

**Compliance review**: every plan produced by `/sp.plan` MUST pass a Constitution Check against
the principles in this document before implementation begins, and any violation MUST be justified
in that plan's Complexity Tracking table or resolved by changing the approach — violations are
never silently accepted.
